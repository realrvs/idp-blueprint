# ADR-0005: RAG vs MCP — гибридная схема доступа к знаниям

- **Статус:** Proposed
- **Дата:** YYYY-MM-DD
- **Авторы:** Platform Team
- **Контекст blueprint:** [docs/blueprint.md](../blueprint.md)

## Контекст и проблема

RAG покрывает документацию (TechDocs, ADR, runbooks), но не покрывает
API, Git-историю, CI/CD-метаданные, observability. Для platform engineering
это gap: значительная часть знаний платформы не является текстом и не может
быть эффективно векторизована. Попытка «загнать всё в RAG» приводит к постоянной
борьбе с устареванием индекса и потере структуры (граф каталога, статусы деплоя).

MCP определяет протокол, через который модель напрямую вызывает инструменты
и получает структурированные ответы — актуальные в момент запроса.

## Рассмотренные варианты

1. **Только RAG** — всё превращается в текст и векторизуется.
   Минус: устаревание, потеря структуры, невозможность действий.
2. **Только MCP** — все знания через tool-calling.
   Минус: дорого и медленно для «медленных» знаний (документация), избыточно
   для статичного контента.
3. **Гибрид: RAG как один из инструментов MCP** — RAG для медленных знаний,
   MCP для быстрых знаний и действий.

## Решение

Вариант 3. RAG выставляется как MCP-инструмент `rag.query`. Агент сам решает,
когда искать по документам, а когда — запрашивать живой API. Границы
применимости зафиксированы в разделе 2.6 blueprint.

## Последствия

### Положительные
- Актуальность: структурированные данные запрашиваются в момент вызова.
- Действия: агент может не только читать, но и выполнять (в рамках прав).
- Гибкость: RAG остаётся для документации, не конкурируя с MCP.

### Отрицательные
- Tool-calling может быть на порядки дороже RAG по токенам и latency.
- Нужен бюджет токенов и circuit breaker (раздел 5.4).
- Нужна инструкция в system prompt, чтобы агент не «перекашивался» в RAG.

## Критерий пересмотра

- MCP-инструменты станут настолько дешёвыми, что RAG потеряет смысл — или наоборот.
- Появление новых классов знаний, не покрываемых ни RAG, ни MCP.
