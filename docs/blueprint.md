## 1. Контекст и цели

### 1.1 Проблема

Платформенные знания фрагментированы: документация живёт в вики, runbooks — в репозиториях, статусы деплоя — в CI/CD, метрики — в observability-инструментах, а решения — в головах инженеров. Разработчик, которому нужно понять «как задеплоить сервис X» или «почему упал деплой Y», вынужден собирать контекст из пяти источников вручную.

Эта фрагментация создаёт три проблемы:

- **Высокая когнитивная нагрузка**: онбординг нового инженера занимает недели, а не дни.
- **Повторное изобретение**: команды решают одни и те же задачи по-разному, потому что не видят существующих решений.
- **Небезопасная интеграция AI**: попытки использовать LLM в SDLC либо ограничиваются «чатом по документации» (RAG), либо дают агенту слишком широкие права — и то, и другое не масштабируется.
### 1.2 Цели

- **Единая точка входа**: разработчик находит каталог сервисов, документацию, шаблоны и статус деплоя в одном интерфейсе (Backstage).
- **Снижение Time to First Deploy**: от «хочу новый сервис» до «сервис в production» — через Golden Path, а не через тикет в платформенную команду.
- **Безопасная интеграция AI**: RAG для документации, MCP для живых данных, Permission Framework для прав — без компромисса по Zero Trust.
- **Управляемое выполнение агентских цепочек**: каждый tool-call аудируется, `forbidden` обрабатывается, circuit breaker останавливает зацикленные цепочки.
- **Актуальность знаний**: индекс RAG инвалидируется по вебхукам, а структурированные данные запрашиваются в момент вызова, а не из устаревшего кэша.
### 1.3 Границы blueprint
**Входит:** архитектура слоев 1–5, паттерны безопасности агентской цепочки,
рекомендации по команде и дорожной карте.

**Вне рамок:** выбор облака/LLM-провайдера, закупка лицензий, детальные runbooks.

### 1.4 Ключевой принцип
> AI-слой не имеет собственных привилегий — он наследует права пользователя.

## 2. Целевая архитектура (5 слоев)

```mermaid

    L1[Слой 1: Интерфейс — Backstage]
    L2[Слой 2: Golden Paths — Templates + Composition]
    L3[Слой 3: Доставка — ArgoCD + Rollouts]
    L4[Слой 4: Guardrails — Kyverno + Secrets]
    L5[Слой 5: Знания и AI — RAG + Agent + MCP]

    L1 --> L2 --> L3
    L4 -.-> L2
    L4 -.-> L3
    L5 -.-> L1
    L5 -.-> L2
```

### 2.1 Слой 1 — Интерфейс (Backstage)

Backstage — единая точка входа для разработчика и для агента. Здесь живут:

- **Software Catalog**: каталог сервисов с владельцами, зависимостями, API-контрактами и SLO. Это граф, а не текст — поэтому агент обращается к нему через MCP (`catalog.getEntity`), а не через RAG.
- **TechDocs**: документация, ADR, runbooks. Это текст — поэтому он индексируется в RAG (`rag.query`).
- **Software Templates**: Golden Paths в виде форм. Разработчик заполняет 3–5 полей, платформа генерирует репозиторий, CI/CD и инфраструктуру.

Слой 1 — единственный, который видит и человек, и агент. Поэтому именно здесь встроен RAG-ассистент и MCP-клиент: они используют один и тот же контекст каталога и документации, но по-разному (см. 2.6).
### 2.2 Слой 2 — Golden Paths

Golden Path — это стандартизированный путь от «хочу сервис» до «сервис работает». Он состоит из трёх частей:

- **Шаблон в Backstage**: форма, которую заполняет разработчик (имя, регион, размер, зависимости).
- **Движок композиции**: Crossplane (или ACK — см. ADR-0001) создаёт составные ресурсы: VPC + EKS + Addons или управляемые сервисы. Разработчик не пишет YAML для инфраструктуры.
- **GitOps-репозиторий**: шаблон генерирует манифесты и коммитит их в репозиторий, который синхронизирует ArgoCD (см. 2.3).

Ключевой принцип: **чем меньше полей заполняет разработчик, тем лучше**. Всё остальное — забота платформенной команды. Если Golden Path не покрывает сценарий, разработчик может «спуститься» на уровень ниже (посмотреть сырые манифесты, отладить) — это escape hatch, а не обход платформы.
### 2.3 Слой 3 — Доставка

Доставка построена на GitOps:

- **ArgoCD** синхронизирует состояние кластера с Git-репозиторием. Единственный источник правды — Git, а не `kubectl apply`.
- **Argo Rollouts** обеспечивает прогрессивную доставку: canary или blue-green с автоматическим откатом по метрикам Prometheus (Analysis Templates).
- **Kargo** (опционально) добавляет оркестрацию промоушена между 3+ окружениями с approval-гейтами. Начинать с Kargo не нужно — см. ADR-0002.

Слой 3 не знает, что источником манифестов может быть агент. Для ArgoCD это просто коммит в Git. Это важно: агент не получает прямого доступа к кластеру, он лишь готовит манифесты, которые проходят через те же guardrails (см. 2.4), что и ручные изменения.
### 2.4 Слой 4 — Guardrails

Безопасность встроена в платформу, а не проверяется постфактум:

- **Kyverno** работает в двух режимах: `dry-run` на этапе дизайна (advisory, не блокирует) и `admission` на этапе деплоя (enforcement, блокирует). Это позволяет разработчику экспериментировать, но гарантирует, что в production попадёт только валидный манифест.
- **External Secrets Operator** синхронизирует секреты из Vault / AWS Secrets Manager в кластер. Разработчик не видит секреты в открытом виде.
- **Permission Framework** (Backstage) проверяет права пользователя на каждое действие агента. Агент не имеет собственных привилегий — он наследует права пользователя (см. 1.4).

Слой 4 — последний рубеж. Даже если агент сгенерировал невалидный манифест или попытался обойти Golden Path, Kyverno отклонит его на admission. Это не заменяет Permission Framework, а дополняет его: Permission Framework решает «можно ли», Kyverno — «валидно ли».
### 2.5 Слой 5 — Знания и AI

Слой 5 — то, что отличает этот blueprint от классического IDP. Он состоит из трёх частей:

- **RAG**: индексирует TechDocs, ADR и runbooks в pgvector. Используется для «медленных» знаний, где актуальность не критична, а стоимость retrieval низкая.
- **MCP Server**: выставляет инструменты платформы (каталог, Kyverno, ArgoCD, observability) как tool-call. Используется для «быстрых» знаний и действий, где важен ответ в момент запроса.
- **Агентская цепочка**: LLM оркестрирует tool-call через MCP, а Permission Framework, Kyverno и circuit breaker обеспечивают безопасность (см. раздел 5).

Ключевой принцип: **RAG — это один из инструментов MCP, а не единственный канал знаний**. Агент сам решает, когда искать по документам (`rag.query`), а когда — запрашивать живой API (`catalog.getEntity`). Границы применимости зафиксированы в 2.6 и ADR-0005.
### 2.6 RAG vs MCP: границы применимости

RAG и MCP решают разные задачи. RAG превращает AI в «читателя документов»,
MCP — в «полноценного клиента платформенных API». Для platform engineering
это принципиальный сдвиг, потому что значительная часть знаний платформы
не является текстом.

| Тип знания | Источник | Способ доступа | Почему |
| :--- | :--- | :--- | :--- |
| Документация, ADR, runbooks | TechDocs | RAG (через MCP-инструмент `rag.query`) | Медленные знания, актуальность не критична, стоимость retrieval низкая |
| Каталог: владельцы, зависимости, API | Backstage Catalog | MCP (`catalog.getEntity`, `catalog.getDependents`) | Граф, а не текст; нужен точный ответ в момент запроса |
| Статус деплоя, CI/CD | ArgoCD, CI | MCP (`deployments.getStatus`) | Меняется каждую секунду; индекс не успеет |
| Политики и их нарушения | Kyverno | MCP (`kyverno.dryRun`, `kyverno.getViolations`) | Структурированный ответ, нужен для решения |
| Метрики, логи, трейсы | Observability | MCP (`metrics.query`, `logs.search`) | Динамические данные, RAG неприменим |

**Принцип:** RAG выставляется как один из инструментов MCP-сервера,
а не как единственный канал знаний. Агент сам решает, когда искать по документам,
а когда — запрашивать живой API. См. ADR-0005.

## 4. Процесс SDLC с IDP

### 4.1 Диаграмма процесса

```mermaid
flowchart LR
    N1[proposal] --> N2[specs] --> N3[design] --> N4[threat-model] --> N5[adr] --> N6[api-contract] --> N7[test-specs] --> N8[tasks] --> N9[apply]

    RAG[(RAG)] -.-> N1 & N2 & N4 & N5
    CAT[(Catalog)] -.-> N1 & N3 & N6
    POL[(Policy-as-Code)] -.-> N4 & N9
    AG{{Agent}} -.-> N1 & N7 & N8 & N9
```

### 4.2 Что меняется на каждом шаге

| Шаг | Без IDP | С IDP |
| :--- | :--- | :--- |
| proposal | Пустой документ | Шаблон + RAG-контекст |
| specs | Вручную | Генерация + валидация против стандартов |
| design | Вручную | Golden Path выбирает композицию |
| threat-model | Post-factum | Автогенерация + Kyverno dry-run |
| adr | Теряется в вики | TechDocs → RAG → контекст будущих решений |
| api-contract | Вручную | Генерация + openapi-diff |
| test-specs | Отдельно | Из контракта + шаблоны |
| tasks | Вручную | Draft backlog от агента, sign-off Tech Lead |
| apply | kubectl apply | ArgoCD + Kyverno admission + Permission Framework |

### 5.3 Hardening
- **Token Exchange (RFC 8693):** scoped-токен с `aud=mcp-server`, TTL 30–60 с. См. ADR-0003.
- **Mid-flight revocation:** `introspect` с Redis-кэшем TTL 5–10 с + события отзыва сессий от IdP.
- **Маскирование в аудите:** PII/секреты в параметрах tool-call — детекция и хэширование.

### 5.4 Circuit Breaker
<!-- State machine + sequence diagram. -->

**Триггеры:**
- 2 `forbidden` подряд.
- N ошибок tool-call подряд.
- **Превышение бюджета токенов на цепочку** — отдельно для RAG-инструментов
  и MCP-инструментов. Tool-calling может быть на порядки дороже RAG;
  агент, застрявший в цикле вызовов, сожжёт бюджет быстрее.
- Явный `forbidden` на критичный инструмент (например, `deploy:*`).

### 5.5 Что явно запрещено
- JWT в промпте или в контексте LLM.
- Проброс точной причины `forbidden` в LLM.
- Повторные попытки обхода `forbidden` агентом.
- Админские инструменты в allowlist MCP.

## 6. Команда и роли

### 6.1 Костяк (3–5 человек)

| Роль | Зона ответственности |
| :--- | :--- |
| Платформенный инженер / Backend | Backstage, MCP Server, RAG-плагин |
| Инженер автоматизации / IaC | Crossplane/ACK, Terraform |
| DevOps/SRE | ArgoCD, Rollouts, кластеры, мониторинг |
| Security / Policy-as-Code | Kyverno, External Secrets, Permission Framework |

### 6.2 Роли поверх костяка
- **Product Owner платформы** (0.5 ставки) — голос разработчика, приоритизация.
- **Frontend/DevEx** (опционально) — UX Backstage и RAG-ассистента.

### 6.3 Масштаб

| Размер организации | Рекомендация |
| :--- | :--- |
| < 100 инженеров | 1 выделенный инженер |
| 100–500 | 3–5 человек |
| 500+ | 6–10+, разделение на подкоманды |

## 9. Риски и открытые вопросы

### 9.1 Принятые риски и меры

| Риск | Мера |
| :--- | :--- |
| Security by Checkbox в threat-model | Async sign-off для high/critical + Kyverno dry-run |
| Галлюцинации при декомпозиции tasks | Draft backlog + sign-off Tech Lead |
| Устаревание индекса RAG | Инвалидация по вебхукам + `commit_sha` в чанках |
| Privilege escalation через агента | Impersonation + circuit breaker + allowlist |
| Shadow agents | Платформа как единственный безопасный путь |
| Перекос в сторону RAG: агент ищет всё в документах, хотя часть знаний — в API | Явное разделение в 2.6 + инструкция в system prompt: «для статуса/каталога/политик — вызывай MCP-инструмент, не ищи в RAG» |
